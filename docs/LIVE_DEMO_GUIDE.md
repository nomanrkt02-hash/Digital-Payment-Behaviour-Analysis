# Live Demonstration Guide

Everything here is **SYNTHETIC** - say so at the start of the demo. It proves the *system* works; it is not
real-world performance evidence.

## Which data is where
| What | Where | Use for |
|---|---|---|
| Built-in demo data | `data/sample/demo_transactions.csv` (1,500 customers, 24 months) | the **Explore Demo Data** button |
| Live upload file (CSV) | `data/live_demo/live_demo_upload_synthetic.csv` | **Upload Dataset** - the main live demo |
| Same file as Excel | `data/live_demo/live_demo_upload_synthetic.xlsx` | show XLSX support |
| Messy file | `data/live_demo/live_demo_messy_synthetic.csv` | validation **warnings** (duplicates, bad dates, blanks, negatives, cancelled) |
| Missing column | `data/live_demo/live_demo_missing_column.csv` | validation **error**: "Missing required column: customer_id" |
| No repeat customers | `data/live_demo/live_demo_insufficient_history.csv` | validation **error**: insufficient history |

The upload file deliberately uses *different column names* (`Customer Unique ID`, `Order Purchase Timestamp`,
`Payment Value` ...) so you can show that columns are detected automatically.
Regenerate any time: `python -m scripts.make_live_demo_files`.

## Suggested 6-minute flow
1. Welcome -> **Upload Dataset** -> drop the messy file -> point at warnings (not crashes) -> then the missing-column file -> readable error.
2. Upload `live_demo_upload_synthetic.csv` -> validation shows records, customers, date range, detected columns.
3. Overview: status mix, return trend (observed history), customers needing attention.
4. Open the story customers below. Ask the audience *"what would you do?"* before showing the recommended action.
5. Settings -> switch to **fit the model on the uploaded data** (`retrain=True`) -> numbers change a little
   (e.g. at-risk 216 -> 263): "the model adapts to the business's own history".

## Story customers (hand-designed, in `live_demo_upload_synthetic.csv`)
| ID | Story | Result with the saved model* |
|---|---|---|
| C001 | Orders every 10-15 days, silent for 45 days (the blueprint's "pizza" customer) | **At Risk**, ~17% return likelihood, Medium value -> retention offer |
| C002 | Very regular, ordered 3 days ago | **Loyal**, High value -> VIP benefits, no discount |
| C003 | Big spender (~Rs 5,200 per order) gone quiet for 62 days | **At Risk + High value** -> strongest retention incentive (shows value and risk are separate) |
| C004 | Small spender (~Rs 110 per order) but extremely regular | **Loyal + Low value** -> loyalty points (shows a low spender can be loyal) |
| C005 | Only one order | **Not enough history** - not scored (honest, no fake prediction) |
| C006 | Gaps keep growing, then 50 days silence | borderline: **Active** (~52%) with the saved model, **At Risk** (~43%) when the model is fitted to this file |
| C007 | New customer, 3 recent orders | **Active** |
| C008 | Usual 10-15 days, silent 35 days | borderline **Active** (~55%) - "the system is unsure, watch closely" |

\* Exact percentages can shift by a few points if the model is retrained on another machine. C001-C005 and C007
are checked by automated tests (`tests/test_analytics_and_robustness.py`); C006 and C008 are *intentionally borderline*.

## Be ready for these viva questions
* **"Is this real data?"** No - synthetic, generated by `src/demo_data.py` and `scripts/make_live_demo_files.py`. The pipeline is identical for real data.
* **"Why not just use days since last order?"** The system compares each customer with *their own* usual interval; a 35-day gap is normal for a monthly buyer and alarming for a weekly buyer. The evaluation report shows the naive rule is clearly weaker than the model.
* **"How do you avoid data leakage?"** Features use only orders up to the snapshot date; the label looks 30 days ahead; split is by time. A unit test proves future orders do not change features.
* **"Is the recommendation another AI model?"** No - rule-based layer on top of the prediction (`src/recommendation_engine.py`).
